01 · โจทย์และข้อมูล

ปัญหา: เข็มในมหาสมุทรข้อมูล

ข้อมูลประกอบด้วย 3 ตาราง คือ transactions (24.4 ล้านแถว, 2.35 GB), cards (6,146 ใบ) และ users (2,000 คน) ซึ่งมีขนาดใหญ่เกินกว่าที่ pandas บนเครื่องเดียวจะ join และทำ window feature ได้สบาย ๆ เราจึงใช้ Spark ทั้ง pipeline ส่วนความยากหลักคือ class imbalance เพราะ fraud มีเพียง 1 ใน 819 รายการ โมเดลที่ทายว่า "ปกติ" ทุกรายการจะได้ accuracy 99.88% แต่จับ fraud ไม่ได้เลย

จำนวน fraud ต่อปี

จำนวนรายการ fraud ในแต่ละปี (ปี 2020 มีข้อมูลถึงเดือน ก.พ. เท่านั้น)

Fraud เกิดเป็น ช่วง ๆ ไม่สม่ำเสมอ เช่นปี 2011 มีเพียง 55 รายการ แต่ปี 2010 มี 3,835 รายการ ทำให้ต้องระวังว่าแต่ละ split มี fraud จากหลายช่วงเวลา

02 · Exploratory Data Analysis

Fraud มีหน้าตาแบบไหน

ตัวเลขทุกตัวในส่วนนี้คำนวณจากข้อมูลดิบครบทั้ง 24.4 ล้านแถว อัตรา fraud เฉลี่ยของทั้งชุดอยู่ที่ 0.122% ซึ่งใช้เป็นเส้นอ้างอิงในกราฟ

อัตรา fraud ตามช่องทางการจ่าย

% ของธุรกรรมในแต่ละช่องทางที่เป็น fraud

ธุรกรรม Online มีอัตรา fraud 0.68% หรือ 16 เท่าของการรูดบัตร และคิดเป็น 62% ของ fraud ทั้งหมด ทั้งที่มีสัดส่วนเพียง 11% ของธุรกรรม

อัตรา fraud ตามตำแหน่งร้านค้า

แยกตามข้อมูล merchant state ที่มีในธุรกรรม

ธุรกรรมกับร้านต่างประเทศมีอัตรา fraud 4.1% หรือ 181 เท่าของร้านในสหรัฐฯ ส่วนการไม่มี zip/state (เกิดกับธุรกรรม online) คือสัญญาณที่โมเดลใช้มากที่สุด

อัตรา fraud ตามชั่วโมง

% fraud ของธุรกรรมในแต่ละชั่วโมงของวัน

สัดส่วน fraud สูงสองช่วงคือ ตี 3 – ตี 5 ซึ่งปกติแทบไม่มีคนใช้บัตร และ 9:00 – 14:00 (0.15–0.19%) ขณะที่หลัง 20:00 ต่ำกว่า 0.03%

อัตรา fraud ตามยอดเงิน

% fraud ในแต่ละช่วงยอดเงิน (USD)

ยิ่งยอดสูง สัดส่วน fraud ยิ่งสูง โดยยอด $250+ มีอัตรา ~1% และ median ของรายการ fraud อยู่ที่ $71 เทียบกับ $30 ของรายการปกติ

ประเภทร้านค้า (MCC) ที่อัตรา fraud สูงสุด

นับเฉพาะ MCC ที่มีธุรกรรมมากกว่า 20,000 รายการ

กลุ่มที่เสี่ยงที่สุดคือท่องเที่ยวและที่พัก (โรงแรม Hilton, Marriott, Wyndham, เอเจนซีท่องเที่ยว, รถเช่า) และสวนสนุก ซึ่งมีอัตรา fraud 0.7–1.4% หรือราว 6–12 เท่าของค่าเฉลี่ย
03 · Big Data Pipeline

จาก CSV 2.35 GB สู่โมเดลใน Model Registry

ทุกขั้นตอนเขียนด้วย PySpark DataFrame API และเก็บผลลัพธ์กลางเป็น Parquet บน Google Cloud Storage เพื่อให้รันต่อจาก checkpoint ได้โดยไม่ต้องคำนวณใหม่ทั้งหมด

Ingestอ่าน CSV 3 ตารางเข้า Spark แล้ว cast ชนิดข้อมูลและล้างเครื่องหมาย $
Join & CleanJoin transactions กับ cards/users (broadcast ตารางเล็ก) แล้วสร้าง timestamp
Feature Eng.ใช้ Window function ต่อ user และต่อ card ดูเฉพาะอดีตของแต่ละรายการ
Splitแบ่ง Train / Valid / Test ประมาณ 70/15/15 และบันทึกเป็น Parquet
Imbalanceเก็บ non-fraud ไว้ 40% และให้ class weight แก่ fraud เท่ากับ √(neg/pos) = 18.3
Train RF120 trees, maxDepth 16, maxBins 64, minInstances 15, subsampling 0.8
ThresholdGrid 0.01–1.00 บน validation แล้วเลือกจุดที่ F1 สูงสุด = 0.56
Evaluate & Saveประเมินบน test ครั้งเดียว แล้วบันทึก model, metrics และ feature importance ลง GCS

ขั้น train บนเครื่อง local ติด Java OOM จึงย้ายไปรันบน Spark cluster (GCP) โดยปรับ repartition และ persist แบบ MEMORY_AND_DISK

07 · ข้อจำกัดและงานต่อไป

ถ้าจะนำไปใช้จริง

ข้อจำกัด

  • Synthetic data — ข้อมูล IBM TabFormer สร้างจาก simulation ดังนั้น pattern บางอย่าง เช่นการกระจุกตัวของ fraud ในบางปี อาจไม่ตรงกับโลกจริง
  • Recall 47% — ยังมี fraud ราวครึ่งหนึ่งที่หลุดรอด ต้องใช้คู่กับกฎ (rule-based) หรือการตรวจสอบโดยคน
  • Validation ยังไม่ใช่ production — ยังไม่ได้ทดสอบแบบ train ด้วยอดีตแล้วทำนายเดือนถัดไปต่อเนื่อง (rolling) ซึ่งใกล้กับการใช้งานจริงกว่า
  • Threshold จาก F1 — ยังไม่ได้คิดต้นทุนจริงของ false negative เทียบกับ false positive

Next steps

  • ใช้ PR-AUC และ recall@precision เป้าหมาย (เช่น precision ≥ 20%) เป็น metric หลัก
  • เลือก threshold จาก expected cost โดยเทียบมูลค่าความเสียหายจาก fraud กับต้นทุนการตรวจสอบและประสบการณ์ลูกค้า
  • ทำ temporal validation แบบ rolling window ตามเดือน เพื่อจำลอง production
  • ลอง Gradient-boosted trees (GBT / XGBoost on Spark) และ feature ด้าน merchant risk score
  • ทำ monitoring สำหรับ data drift และ retrain อัตโนมัติผ่าน model registry ที่มีอยู่แล้ว
